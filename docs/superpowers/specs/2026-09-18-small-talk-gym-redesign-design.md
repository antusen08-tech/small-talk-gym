# Small Talk Gym 重新规划 · 设计稿

> 本文件基于《产品策划与内容交接稿.md》与《初阶Coach内容库.md》，把产品方向、技术架构与 UI 视觉方向一起定稿，供下一步写实现计划使用。产品原则、内容结构、Coach/Simulator 的边界机制等，交接稿中已确认的部分本文件不重复展开，只在涉及架构落地时引用。

## 1. 重新规划的动机

现有 HTML 原型（`index.html`）是纯演示品：每张 Coach 卡片和 Simulator 场景都写成独立的 HTML 片段 + 专用 JS 函数，内容和界面焊死在一起，无法扩展，AI 对话也是假的。本次重新规划的三个不满意点：

1. **差异化不够**——单看界面，和市面上的 AI 陪聊 / 习惯打卡 / 社交技巧内容类产品区分不明显。
2. **实现路径不清楚**——不知道从"一个 HTML 原型"到"10 人能实际用的 app"要走哪几步。
3. **内容留存存疑**——不确定内容和机制能不能让用户持续回来用。

## 2. 差异化结论

参照三类产品（AI 聊天陪练、自我提升/习惯类、社交技巧内容类），确定的差异化方向是**三者结合**：内容（Coach 的原理讲解）+ 结构化模拟（Simulator 的场景卡）+ 训练感（一次一小步、可完成的来回）。

核心差异化不是靠更聪明的台词，而是靠架构：**Simulator 的每一轮 AI 回复都被场景卡的结构化规则（地点/关系/当前话题线/绿黄红灯）约束**，不是自由聊天。见第 4 节。

## 3. 整体架构

```
浏览器（前端 Web App）
   │  fetch / realtime
   ▼
Supabase（Postgres 数据库 + Auth + Edge Functions）
   │  Edge Function 转发
   ▼
LLM API（Claude，仅用于 Simulator 对话轮）
```

- **前端**：单页 Web app（React/Vite，静态部署，如 Vercel）。不再是"每张卡一段 HTML"，而是两个通用组件驱动：`CoachCardPlayer`、`SimulatorChatPlayer`，都从数据库读数据渲染。
- **后端**：不自建服务器。用 Supabase 提供 Auth + Postgres + Edge Function（Edge Function 负责组装 prompt 调 LLM，避免把 API key 暴露在前端）。
- **AI**：只有 Simulator 对话轮调用 LLM；Coach 是纯数据展示 + 前端本地判分，不调用 AI（省成本，也符合"Coach 教原则，不需要生成式内容"的定位）。
- **技术选型理由**：Web app 最小可行技术栈，10 人测试阶段不需要上架审核，能最快验证。

## 4. 数据模型（内容数据化）

四张表，直接对应交接稿已定义的结构：

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `skill_cards` | Coach 技能卡 | `level`(初/中/高), `skill_order`, `title`, `principle`, `when_not_to_use`, `scenario_text`, `choices`(json，含对错与反馈文案), `illustration_url` |
| `scenario_themes` | Simulator 大类 | `category`(日常/工作/社交/专业), `title`, `description` |
| `scene_cards` | Simulator 具体小情境（一个 theme 下 3–5 张） | `theme_id`, `location`, `moment`, `relationships`, `current_thread`, `goal`, `green_light`, `yellow_light`, `red_light`, `off_limits_notes` |
| `practice_records` | 我的记录 | `user_id`, `scene_card_id`/`skill_card_id`, `completed_at`, `user_reflection_text`, `milestone_flag` |

加内容 = 往表里插一行，不碰前端代码。`初阶Coach内容库.md`（20 张卡）可直接导入 `skill_cards`。

## 5. Coach 流程

`CoachCardPlayer` 读 `skill_cards`，按 `level` + `skill_order` 顺序渲染统一 UI：讲原理 → 出题（选择/排序/自由作答）→ 前端本地判断给反馈 → 下一张。完成一个 level 的所有卡才解锁下一 level。不调用 AI。

## 6. Simulator 流程 + 边界机制（差异化核心）

1. 用户选 `scenario_theme` → 选一张未练过的 `scene_card`（默认推荐新的，可选重练）。
2. 前端把该 `scene_card` 的全部字段 + 对话历史，通过 Edge Function 发给 LLM，**系统 prompt 显式写入**：
   - 场景的地点/时刻/关系/当前对话线；
   - 绿黄红灯规则；
   - 边界判定指令：模型须判断用户输入是"符合当前话题线"／"有点跳题但可接"／"明显越界"，分别对应"自然继续角色"／"给较短真实回应+可选教练提示"／"暂停该轮+温和说明原因+让用户换说法"；
   - 反馈语气要求：不说"错了"，用场景化解释。
3. LLM 返回结构化 JSON（角色台词 + 判定类型 + 可选教练提示），前端渲染为聊天气泡 + 必要时的提示条。
4. 每轮后台给三个选项：继续一轮 / 自然收尾 / 结束练习，不强迫聊完，默认建议 3–5 轮。
5. 结束后写入 `practice_records`，进入复盘页（用户写感受，可选标记里程碑）。

## 7. 账号与数据

Supabase Auth 用邮箱魔法链接（无密码，适合 10 人测试）。`practice_records`、完成状态都挂在 `user_id` 下，Row Level Security 保证用户只读自己的数据。

## 8. 留存钩子

- "今天"页：非强制推荐，打开时显示"上次练到哪、还有几个新情境没试"，给自然的回来理由，不做 streak 压力。
- "我的记录"：按交接稿第 10 节，只显示已练情境数/总数的小角标，详细历史在"我的记录"里。
- 场景库持续扩展新 `scene_card`，让同一技能在新情境里反复被验证，这是内容层面的复玩理由。

## 9. UI 视觉方向

### 9.1 调性决策过程

最初探索了"日系克制 + 暖色手写"方向（极简留白、米白纸感），后改为**3D 软阴影卡片风（claymorphism 的克制版）**，主色调从参考图的紫色系改为**蓝紫色系**（原因：暖褐色底色与语义色图标——绿/红/蓝——撞色，蓝紫色底色能让语义色图标保持清晰区分）。

### 9.2 视觉与实现的关键判断：插画和 UI 组件要拆开生产

用户提供的参考图是**照片级 3D 渲染图**（推测产自 Blender/Spline 类 3D 工具或 Midjourney 类 AI 图像模型），不是网页 UI 元素。CSS 无法做到同等质感，原因：

1. 没有统一光源——CSS 阴影是逐元素手调数值，不是物理光照计算，做不出跨元素一致的光影关系；
2. CSS 渐变是平涂分层，做不出粘土材质的次表面散射（边缘透光的软糖感）；
3. 浏览器渲染精度做不到照片级的抗锯齿曲面过渡。

**采用的方案**：拆开生产两类资产——

- **插画/角色类**（首页大图、空状态、完成页、引导页）：用 AI 图像生成工具（如 Midjourney/Gamma image 等）单独产出静态图片或动画素材，可以做到接近参考图的照片级质感。
- **可交互 UI 组件**（按钮、卡片、列表行）：用一套克制版的软阴影组件系统实现，浏览器可实时渲染、可维护、性能可控，不追求照片级立体，但保留清晰的悬浮/层次感。

这是业内常见做法（如 Duolingo、Cash App）：立体软萌的角色是预渲染素材，实际按钮/卡片用更简化的组件系统。

> **待办（不在本次范围内）**：AI 插画的实际产出因 Gamma 图像额度不足而跳过，本次只确定了方向和文字 brief（见下）。正式产出插画素材是后续独立任务。

### 9.3 插画 Brief（供后续产出使用）

- 材质：3D 粘土渲染（claymorphism），哑光带轻微高光，非卡通儿童风；
- 色调：暖色调角色配色 + 蓝紫色系背景/UI 呼应，柔和渐变；
- 情绪：低压力、友善、平静，不夸张、不浪漫化（沿用交接稿第 11.1 节插图原则：不默认男女搭配，穿插不同性别组合、不同人生阶段）；
- 构图：单人物/场景为主，柔和环境光，阴影投射体现悬浮感。

### 9.4 UI 组件系统（最终基线）

- **背景**：蓝紫色对角渐变（`#bcd6f7 → #8fb8ef → #6f9de6`），叠加一道柔和斜向高光模拟光线；
- **外层卡片**：浅蓝白渐变底、大圆角（32px）、外阴影 + 内高光模拟悬浮感；
- **列表行**：白底、独立阴影（比外层卡片阴影更贴近，制造"浮在卡片表面"的层次感）；已完成状态用蓝色渐变填充反色；
- **图标块**：小圆角方形，语义色渐变（绿=完成、蓝=默认/中性、橙=提醒/新内容），避免和背景色系冲突；
- **按钮**：胶囊形，主按钮用蓝色渐变+阴影，次按钮白底浅阴影；
- **底部导航**：悬浮磨砂胶囊条，四个一级菜单图标，当前项高亮为蓝色渐变图标块；
- 这套系统适用于"今天""学习""练习""我的记录"所有页面，Simulator 对话气泡沿用同一阴影/圆角语言（对方气泡白色、用户气泡蓝色渐变）。

## 10. MVP 范围

- 4 个一级菜单（今天/学习/练习/我的记录），沿用 9.4 的视觉系统；
- Coach 初阶 5 技能（数据来自 `初阶Coach内容库.md`，导入 `skill_cards`）；
- 3 个 Simulator 主题，每主题 3–5 张场景卡（"跨部门咖啡局"素材可复用，其余需新写）；
- 邮箱魔法链接登录、Supabase 存储、Claude API 接 Simulator；
- 部署到 Vercel，供 10 人测试。

不做：付费、订阅、排行榜、推送通知、"表达影响力"路径、照片级插画的实际产出。
